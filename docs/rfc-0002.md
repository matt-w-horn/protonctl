# RFC-0002: Writes that cannot reach what you made, and Photos

| | |
|---|---|
| **Status** | Proposed. Nothing here is built. If accepted, Stage 1 amends [RFC-0001](rfc-0001.md)'s R1 and Q5. |
| **Decides** | Q44 to Q51 ([Open questions](#open-questions)). Each has a recommendation. |
| **Platform** | macOS. Linux keeps what RFC-0001 built; nothing here is planned for it. |
| **Numbering** | Continues RFC-0001: requirements from R27, questions from Q44. |

## Summary

- **Recommendation.** Let protonctl write again in three stages, and
  build only Stage 1 now. Stage 1 cannot change or remove anything the
  user made:
  - It writes new text files into the local export folder, outside the
    Proton Drive app's folder.
  - It creates plain-text reply drafts in Proton's Drafts. It never sends,
    replaces or deletes a draft.
  - It adds labels whose names start with a fixed prefix. It never
    removes a label, moves a message or changes a flag.
- **Stage 2**, writes into a Drive folder in Proton's cloud, and
  **Stage 3**, organizing mail and editing the user's own files, are
  recorded with the requirements a design review found they need. Each
  needs its own decision.
- **Never, in any stage:** send mail, share, create a public link, invite,
  answer an invitation, delete anything permanently, empty the trash, or
  change account settings. R1's ban on sending data outside the account
  stays as it is.
- **Why Stage 1 first.** RFC-0001 made protonctl read-only (Q5), because a
  missing capability beats an approval prompt that users answer yes to
  about 93% of the time (Anthropic's figure, cited in RFC-0001). Stage 1
  keeps that property for everything the user made. The worst that
  injected text can get from Stage 1 is clutter: stray files in a local
  folder, drafts the user deletes, and labels the user clears. A draft the
  user sends without reading is the one path out, and it was open before:
  the user can always send what Claude writes.
- **Other services.** Of Proton's other products, only Photos can be read
  through an official client (the Drive CLI). Docs and Sheets have no read
  path: the Drive CLI skips them by design, and the Drive app keeps only an
  empty placeholder. Contacts, Meet and Lumo have no local access, and
  Calendar has no write path. Pass stays out.

## Workflows

Eight common tasks, chosen to differ, and what Stage 1 does for each.

| # | Task | What protonctl does in Stage 1 |
|---|---|---|
| W1 | Draft replies to this week's open threads | reads the threads and creates one plain-text draft per thread; the user edits and sends in Proton |
| W2 | Brief me before the planning meeting | reads the event, related threads and files, and writes `Briefs/Planning.md` in the export folder |
| W3 | Collect this year's receipts for taxes | saves each receipt into the export folder with `get_attachment` and `download_file` and `export: true`, as built, then writes an index file beside them |
| W4 | Keep a running project log | writes a new file in the export folder for each entry; it never edits an earlier one |
| W5 | Triage newsletters and bills | adds `Claude/Newsletters` and `Claude/Bills` labels; the user archives or stars by label in Proton |
| W6 | Tidy the scans folder | writes a plan into the export folder: each rename and move, one per line; the user carries it out |
| W7 | Put these dates on my calendar | writes an `.ics` file into the export folder with no attendees or organizer; the user imports it in Proton Calendar |
| W8 | Prepare a pack for my accountant | as W3; the user moves the folder into Drive and shares it, since protonctl cannot |

Stage 1 covers each task. Stages 2 and 3 would remove the last manual
step from W2, W5, W6 and W8, at the cost their requirements set out.

## Proton's write surfaces

What Proton's official clients can write. The Drive CLI's commands come
from the installed CLI 0.8.0 (`proton-drive --help`) and its source;

(`internal/services/imapservice/connector.go`) and Proton's support page
on labels in Bridge.

| Calendar | none: the share link is read-only, and Proton offers no calendar API | none |

## Stage 1

### Files in the export folder

`write_export_file` writes one new text file into the export folder that
`[export] folder` names (RFC-0001, R10). It never replaces a file, so W4
writes a new file per entry. It writes through a directory opened once
with no symlink followed, the same way the export fixes of the security
assessment do (S1 and S2), so a symlink that another program plants
cannot redirect it. The export folder must already be outside the Proton
Drive app's folder, so nothing it writes reaches Proton.

An `.ics` file loses every `ATTENDEE`, `ORGANIZER` and `METHOD` line
before it is written. An import of such a file then sends no invitation
and no reply, which keeps R1's "no attendees".

### Drafts

`create_draft` appends one draft to Drafts through Bridge. It never sends.
It never replaces or removes a draft, its own included: removing a draft
in Bridge deletes it permanently, and the user may have edited it in the
meantime. The user deletes unwanted drafts in Proton.

A draft is plain text, with no HTML and no attachments, so nothing in it
can be hidden in a collapsed quote or load a remote image. It answers a
thread that the caller names, and every recipient must already appear in
that thread's From, To, Cc or Reply-To headers. protonctl builds the
headers itself from the fields it accepts, refuses a line break or a NUL
in any of them, and writes no Bcc or `Resent-` header.

The recipient rule does not stop a reply to an attacker who wrote to the
user: the attacker is in their own thread. What stops that is the user
reading the draft before sending it, and plain text keeps all of it
visible.

### Labels

`add_label` adds a label to messages. The label's name must start with
the prefix `Claude/` (Q45), and protonctl may create such a label if it
does not exist. It adds labels only: it never removes one, never moves a
message between folders, and never changes the read or starred state.
So nothing leaves the Inbox, and an alert stays where the user would see
it.

### Turning Stage 1 on

The config's `[writes]` table turns on each of `files`, `drafts` and
`labels`; all three are off by default (Q48). A tool whose capability is
off is not listed. Each write call reads the config again and refuses if
its capability is off, so turning one off takes effect at the next call.

The config is the user's file, and in Claude Code the model can edit it
unless the README's sandbox settings deny that, as they do for the
exclusions today (RFC-0001, Q17). For Stage 1 that is acceptable: what
the model gains by turning a capability on is clutter. Stages 2 and 3
need a boundary that the model cannot cross, and the config is not one.

### Tools

| Tool | Capability | `readOnlyHint` | `destructiveHint` | `idempotentHint` |
|---|---|---|---|---|
| `write_export_file` | files | false | false | false |
| `create_draft` | drafts | false | false | false |
| `add_label` | labels | false | false | true |

## Stage 1 requirements

- R27. Every write tool MUST be off unless the config's `[writes]` table
  turns its capability on. A tool whose capability is off MUST NOT be
  listed, and a call to it MUST be refused. Each write call MUST read the
  config again before it writes.
- R28. `write_export_file` MUST create a new file in the export folder
  and MUST NOT replace one. Its name MUST be one or more path parts, each
  a single name with no `/`, `\`, `.` or `..` part and no control
  character. It MUST open each folder relative to the export folder with
  no symlink followed, and create the file the same way. It MUST accept
  only `.md`, `.txt`, `.csv`, `.json` and `.ics`, at most 1 MiB. An
  `.ics` file MUST lose every `ATTENDEE`, `ORGANIZER` and `METHOD` line.
- R29. `create_draft` MUST create a draft only by `APPEND` to the Drafts
  mailbox. The draft MUST be `text/plain` in UTF-8 with no attachment. It
  MUST name a thread, and every recipient MUST appear in that thread's
  From, To, Cc or Reply-To. protonctl MUST build the headers from its
  fields, MUST refuse CR, LF and NUL in every field, and MUST write only
  From, To, Cc, Subject, In-Reply-To, References, Date, Message-ID,
  MIME-Version and Content-Type. It MUST NOT send, replace or remove any
  message.
- R30. `add_label` MUST only `COPY` messages from All Mail to a label
  mailbox whose name starts with `Labels/Claude/`, checked against the
  mailboxes `LIST` returns. It MAY `CREATE` a mailbox under that prefix.
  It MUST NOT `STORE` a flag, `MOVE`, `EXPUNGE`, or delete or rename a
  mailbox.
- R31. protonctl MUST NOT implement sending, sharing, public links,
  invitations or answers to them, permanent deletion, trashing, emptying
  the trash, photo uploads, album changes, or account settings. This is
  R1's first sentence, kept, and the rest of what R1 bans outside Stage 1.
- R32. Each process MUST stop at its budget: by default 100 files, 20
  drafts and 500 labelled messages (Q47). `get_status` MUST report what
  is left.
- R33. Every requirement from R27 to R32 MUST have a test that calls the
  tool over MCP with an adversarial argument (a symlinked folder, a
  recipient outside the thread, a CR in a subject, a label outside the
  prefix, a disabled capability) and sees it refused, each shown to fail
  first. The prompt-injection drill (T12) runs before Stage 1 ships, and
  its outcome is recorded; the tests, not the drill, are the gate.

## Stage 1 threat model

Assets, in order of harm: what the user made, confidentiality towards
third parties, the user's attention, the Proton account's standing (ToS
§2.10), and the Mac's other secrets. Actors: a third party whose text
reaches Claude through mail, a shared file or an invitation; the model,
acting on that text; another program running as the user. Root and access
to the Proton account stay out of scope.

| Threat | Example | Control | Residual |
|---|---|---|---|
| Injected text destroys the user's work | "trash everything in Projects" | no tool replaces, moves, trashes or deletes (R28 to R31) | none known |
| A file write lands somewhere else | a symlink planted in the export folder by an agent's VM | writes relative to an opened folder, no symlink followed (R28) | none known |
| A file write reaches Proton | the export folder placed in the Drive app's folder | refused when the config loads (RFC-0001, R10) | the user moves the folder into Drive, which is their choice |
| Exfiltration through a draft | a reply to an outside address carries a confidential file's text | recipients from the thread (R29); plain text, so nothing is hidden; no send | the user sends a draft without reading it |
| A beacon in a draft | an `<img>` that loads an attacker's URL when the draft opens | plain text only (R29) | none known |
| Header injection | a subject with a line break adds a `Bcc` | fields built by protonctl, CR and LF refused (R29) | none known |
| An invitation through an `.ics` | an imported file names the attacker as organizer | attendee, organizer and method lines removed (R28) | none known |
| Hiding an alert | "label the bank's message and archive it" | labels added only; no move, no flags (R30) | none known |
| The model turns writes on | edits `config.toml` | the README's sandbox settings deny config writes | without those settings, the model can turn on Stage 1, whose worst case is clutter |
| Account friction | thousands of drafts look automated (ToS §2.10) | budgets per process (R32) | a long session hits its budget |

RFC-0001's threats stay as they are.

## Stage 2: a workspace in Drive

Stage 2 would let protonctl write into one folder in the user's Drive, so
that files reach the user's other devices without a manual step. A design
review of an earlier draft of this RFC found what it needs. Before Stage 2
is built:

1. Every node from the target and from the destination up to the Drive
   root is checked: not shared, no public link, not trashed. A subfolder
   the user shared inside the workspace would otherwise receive what
   Claude writes.
2. Exclusions (R7) apply to every source, so a copy cannot read an
   excluded file into the workspace.
3. Each new name is one path part, never shaped like a node UID and never
   holding `\/`, which the CLI reads as a lookup by UID and as a `/`
   inside a name.
4. The CLI's lock is held across the checks and the write, and the node
   is checked again after the write. A move by the user between check and
   write otherwise sends the write outside.
5. A new revision names the revision it replaces, and the residual is
   stated: a change in another client between the check and the upload.
6. Budgets count copied bytes as well as uploaded ones, persist across
   processes, and refuse folder copies, because a server-side copy uses
   storage quota that Proton Mail shares; a full quota stops incoming mail.
7. The policy that turns Stage 2 on lives where the model cannot write:
   a root-owned file that only `sudo` changes (Q49). A pseudo-terminal
   passes a "terminal only" check, and a signed protonctl driven through
   one meets no Keychain prompt.
8. Any state Stage 2 keeps lives outside
   `~/Library/Application Support/protonctl`, which `doctor` treats as a
   leftover of aliases mode, and the README's sandbox settings deny the
   model reads and writes there.

## Stage 3: organizing mail, and editing the user's files

Stage 3 would archive, mark read, remove labels, and rename, move, trash
or revise the user's own Drive files. Each of these changes something the
user made, so each needs a user who is present, through a prompt that
neither the model nor another program can answer. macOS offers that in
LocalAuthentication (Touch ID or the login password), but how its prompt
reaches the user from protonctl, a child of the Claude apps, is not
established. Until it is, Stage 3 is not proposed (Q50). What the review
found it would need:

1. Removing a label takes `\Deleted` and `UID EXPUNGE` in that label's
   mailbox, so "never expunge" must become "expunge only in a label
   mailbox checked against `LIST`".
2. Archiving moves a message only from the Inbox, never from a custom
   folder, Sent, Drafts, Trash or Spam, since a move out of a custom folder
   loses where it was, and undo cannot restore it.
3. A log of changes and their inverses is the user's record, never an
   authority: undo checks the live state, and the model cannot read or
   write the log.
4. A proposal to trash or move a folder records every item under it, and
   is refused if any changed.
5. Everything shown in a terminal for the user to approve is escaped as
   R6 escapes Drive paths, so control sequences cannot redraw it.

## Other services

| Service | Official local path | Read | Write | Recommendation |
|---|---|---|---|---|
| Photos | Drive CLI: `photo timeline`, `album list`, `album photos`, `photo download` | yes | never (R31) | offer as a fourth service, off until `setup photos` (Q51) |
| Docs, Sheets | none: the CLI skips them on download ("Proton Docs and Sheets have no downloadable content"), the Drive app holds an empty placeholder, and export is in the web app only | no | no | each Drive tool says so plainly when it meets one, and names the export; protonctl reads the user's `.docx` or `.md` export |
| Contacts | none: no API, no CardDAV, nothing in Bridge; VCF export in the web app | no | no | out, as Q1 decided |
| Calendar | the Full-view share link | yes | no | unchanged; W7 writes an `.ics` for the user to import |
| Meet, Lumo | Proton's apps only; a Lumo API is on Proton's roadmap | no | no | out until an API ships |
| Pass | `pass-cli`, which returns secrets as JSON | yes | yes | out: a password manager is a separate trust domain, and Proton's own `pass-cli agent` gives scoped, audited tokens to anyone who wants it |

Photos is the one new read service, and it is not low-risk: photos carry
faces, documents photographed with a phone, and locations in their EXIF
data. It would follow Drive's rules, with three more: EXIF data, GPS
included, is removed from metadata and from returned images, every time;
an exclusion by album hides a photo that is in that album wherever the
photo appears, the timeline included; and photos come back as images, a
few per call.
